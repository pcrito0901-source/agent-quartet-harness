# 付録（adapters）

このハーネスは **土台** と **付録** の2層でできている。

| 層 | 置き場所 | 中身 |
|---|---|---|
| 土台 | `CLAUDE.md` ・ `.claude/agents/` ・ `.claude/commands/` ・ `docs/` の雛形 | どの技術でも同じに使える決まり（何を守るか） |
| 付録 | `adapters/<名前>/` | 技術ごとの「どうやって」（どこで評価するか ・ 何が手動になるか ・ どう配る ・ どこに罠があるか） |

**付録は土台の「どうやって」を埋めるだけで、「何を守るか」は変えない。**
ぶつかったら土台を優先し、付録のほうを直す。

## 付録の一覧

| 付録 | 使うとき | 主な中身 |
|---|---|---|
| [`web/`](web/README.md) | ブラウザで動くアプリ | 評価の面 ・ CSS のトークン ・ API の入口 ・ 配備 |
| [`expo-react-native/`](expo-react-native/README.md) | Expo / React Native でストアに出すアプリ | Web で評価する理由と限界 ・ `design-tokens.ts` ・ 手動検証 ・ EAS のビルド ・ TestFlight ・ App Store Connect の分担 |
| [`convex/`](convex/README.md) | サーバーが Convex | ローカルと本番が別のサーバー ・ 同期で関数が消える ・ 公開関数の関門 ・ cron ・ `.collect()` ・ `=== null` |

- **組み合わせて使う**（例: `expo-react-native` ＋ `convex` ／ `web` ＋ `convex`）
- **付録の無い技術でも、土台だけで動く**（例: Flutter ＋ Supabase ・ CLI ツール ・ API だけのサービス）。
  そのときは `docs/runbook.md` に評価の面と起動の仕方を書き、踏んだ罠を「既知のハマりどころ」に貯める。
  罠が3つ以上たまったら、付録に切り出す

## 配線のしかた（`/harness-init` がやる）

1. 技術の組み合わせを見分け、`AskUserQuestion` でユーザーに確かめる
2. 選んだ付録の `README.md` を、プロジェクトの `docs/adapters/<名前>.md` に写す（補助ファイルは `docs/adapters/<名前>/`）
3. プロジェクトの `CLAUDE.md` の「使う付録」節に、付録の名前とパスを書く
4. 付録の「土台への差し込み」節の行を、`docs/runbook.md` と `CLAUDE.md` に写す
5. 付録の「スキルの例」から、入っているスキルだけを役ごとに配線する

各エージェントは着手の前に `docs/adapters/*.md` を読み、自分の役に関わる節に従う。

## 付録の書き方（新しい技術を足すとき）

見出しをそろえる（エージェントが同じ場所を探せるように）。要らない見出しは「なし（理由）」と書いて残す。

| # | 見出し | 書くこと |
|---|---|---|
| 1 | 見分け方 | どのファイル ・ 依存があればこの付録を使うか |
| 2 | 評価の面 | 回帰の E2E が何を操作するか ・ なぜそこか ・ 本番の面との差（限界） |
| 3 | 手動検証に回すもの | 自動の面では測れない機能の一覧 |
| 4 | デザイントークン | 正本の形式と使い方 ・ 本番の面で効かない書き方 |
| 5 | サーバーの公開の入口 | 入口の列挙のしかた ・ 認証の関門 ・ 定期処理の呼び方 ・ テスト用の入口の閉じ方 |
| 6 | 配備 ・ ビルド ・ 配布 | コマンド ・ 承認の要る操作 ・ 費用 ・ 台本 |
| 7 | 罠 | 実際に踏んだもの（実害つき） |
| 8 | スキルの例 | 役と場面ごとに（入っていなければ配線しない） |
| 9 | 土台への差し込み | `docs/runbook.md` と `CLAUDE.md` に写す行 |

**実害を必ず添える。** 実害の無い注意書きは読み飛ばされる。
