# 付録: Convex

サーバー（データベース ・ 関数 ・ 定期処理）が Convex のアプリ。
クライアントの付録（[`web`](../web/README.md) ・ [`expo-react-native`](../expo-react-native/README.md)）と組み合わせて使う。

補助ファイル:

| ファイル | 中身 |
|---|---|
| [`list-public-functions.mjs`](list-public-functions.mjs) | 公開の関数を列挙し、認証と開発用の関門の手がかりを表にする（読むだけ ・ 5 の点検の下書き） |

## 1. 見分け方

- `convex/` ディレクトリがある ・ `package.json` に `convex` がある
- `.env.local` に `CONVEX_DEPLOYMENT` がある

## 2. ローカルと本番は別のサーバー

**E2E はローカルのデプロイメント（例: `anonymous:anonymous-<アプリ名>`）を、実機や本番のクライアントはクラウドのデプロイメントを見ていることがある。
同じコミットでも、サーバーのコードは別物でありうる。**

> 実害: ある回が画面の読む欄を足した。ローカルには入ったがクラウドへ同期しておらず、**E2E は全緑のまま、実機には `undefined` が描かれた**。
> ユーザーの「表示がよく分からない」をデザインの問題と読みかけた。原因はサーバーの同期漏れで、アプリは1バイトも悪くなかった。

- **`convex/` を触った回は、実機を試す前に `git diff <最後に同期したコミット>..HEAD -- convex/` が空かを見る。** 空でなければ、実機の報告はまず同期を疑う
- **関数の名前の照合（名簿の一致）は、欄が増えたことを見ない。** 名前が同じまま中身が変わった関数は、名簿の検査では緑になる
- **クラウドのデプロイメントが Convex 上は「dev」でも、実機が見ているなら本番と同じに扱う。**
  配備先ガードのスキル（例: `convex-deploy-guard`）は「prod」にしか同意を求めないことがあるので、そのままだと実機のサーバーへの操作を素通しする
- 同期の前後で `.env.local` の `CONVEX_DEPLOYMENT` がローカルのままかを実測する（ハッシュを比べる）
- 同期したら、同期したコミットと時刻を `status.md` に書く（次の「最後に同期したコミット」になる）

## 3. 同期で関数が消える

同期（`npx convex deploy` や、関数の顔ぶれを両側で一致させる自前の同期）は、**手元で消した公開の関数をクラウドからも消す。**
**端末に入っている古いビルドがそれを呼ぶと、画面が落ちる。** Web の E2E はいつも新しい束で走るので、この壊れ方を構造的に見ない。

> 実害: ある回の同期が公開の関数を2本消した。端末に入っていたビルドは、ある画面を開いた瞬間にそれを呼んでいて、
> 画面が落ちる見込みになった（同期の前表示の「クラウドにあって手元に無い関数 4件」を見ながら確かめていなかった）。

1. 同期の前表示で「クラウドにあって手元に無い関数」を数える
2. 0 でなければ、**最後に配ったビルドの木**（タグ `testflight/<n>` など）で、その名前を `git show <木>:<パス> | grep` する
3. 呼んでいれば、**同期の直後に新しいビルドを出す段取りを先に立てる**。ビルドの承認の条件で止まるなら、同期の前にユーザーへ仰ぐ
4. 消さずに残す道もある（古いビルドがいなくなるまで、空の値を返す関数として残す）

## 4. ローカルのサーバーの起こし方

- `npx convex dev` は、CLI がアカウントにログインしていると「リンクしますか（Y/n）」で止まる。**Y と答えない**（`CONVEX_DEPLOYMENT` が書き換わる恐れ）。
  stdin を端末でないパイプにすると、問いごと飛ばす
- DB が大きいと既定の起動待ち30秒を越える。`CONVEX_LOCAL_BACKEND_STARTUP_TIMEOUT_SECS=180` を**プロセスの環境だけに**渡す（`.env.local` に書かない）
- 起きたかは**プロセスの数ではなく応答**で見る: `http://127.0.0.1:3210/version`
- セッションと一緒に死なないよう、切り離して起こす

## 5. 公開関数の関門（セキュリティ点検）

**`query` ・ `mutation` ・ `action` ・ `httpAction` で export した関数は、URL を知る誰でも呼べる。**
アプリの束に URL が入っているので、「アプリからしか呼ばれない」は守りにならない。

| 入口の種類 | 決まり |
|---|---|
| 利用者のデータを読む ・ 書く | 関数の頭で認証（`ctx.auth.getUserIdentity()` か認証ライブラリの `getAuthUserId`）し、**持ち主やメンバーを照合する** |
| テスト用 ・ シード ・ 開発用のログイン | 開発用の関門（環境変数）の後ろに置き、**本番では閉じる**。閉じたら、本番のデプロイメントで1度呼んで拒まれることを確かめる |
| 定期処理（cron）・ 関数から関数への呼び出し | `internalQuery` ・ `internalMutation` ・ `internalAction` にし、`crons.ts` からは `internal.*` で呼ぶ。**cron から呼ぶために公開にしない** |

- **開発用の設定を閉じても、別の場所で開いている口がある。** 関門は1か所の判定関数にまとめ、テスト用の入口がすべてそれを通るかを一覧で確かめる
  （別の環境変数を見ている口 ・ 関門を通らない口が残る）
- 点検は読むだけで行う: `node docs/adapters/convex/list-public-functions.mjs convex` で下書きを作り、
  レビュー用のスキル（例: `convex-reviewer`）に「書き換えず、指摘だけ」で読ませ、各行を開いて確かめる

> 実害: 提出の直前の点検で、**ログインなしで全利用者の薬の名前やグループ名が読める口が4つ**見つかった。
> どれも開発中に「テストのため」に開けた口で、開発用の設定を閉じた後も別の判定で開いていた。

## 6. 増え続ける表を全部読まない（`.collect()` の上限）

**1回の関数の読み取りには上限がある**（件数とバイト数。値は Convex の公式の Limits を見る）。
記録 ・ 予約 ・ 通知 ・ ログのような**日々増える表を `.collect()` で全部読むと、いつか上限を越えて、その関数ごと（定期処理なら毎回）止まる。**

- `.withIndex(...)` で範囲（利用者 ・ 期間 ・ 状態）を絞ってから読む。絞れないなら `.take(n)` か `.paginate()`
- `.filter()` は読んだ後で捨てるだけなので、読み取りの量は減らない
- 定期処理は1回に処理する件数に上限を置き、残りは次の回か `ctx.scheduler` で続ける
- 運用の数字はスキル（例: `convex-advisor`）で72時間の読み取りの上限の事象を見る

> 実害: 予約の記録を全部読む関数が上限を越え、**テストのデータ作り（シード）が全滅した。**

## 7. `=== null` の罠

古いデプロイメントは、新しく足した欄を**返さない**（`undefined`）。`=== null` で見張ると、**`undefined` は素通りして門が開く。**

```ts
if (view.receivingNow == null) return <Fallback />;   // null と undefined の両方を拾う
const label = view.statusLabel ?? null;                // 畳んでから比べる
```

> 実害: 古いデプロイメントの応答で、`=== null` の門が開いて `undefined` が画面に出た。

## 8. 罠（実害つき）のまとめ

| 罠 | 実害 | 節 |
|---|---|---|
| 同期せずに実機で確かめた | E2E 全緑のまま実機に `undefined` | 2 |
| 同期で公開の関数が消えた | 端末の古いビルドの画面が落ちる見込み | 3 |
| リンクの問いに Y | 接続先が書き換わる恐れ（踏みかけた） | 4 |
| テスト用の口が本番で開いたまま | ログインなしで全利用者のデータが読めた | 5 |
| 増え続ける表の全読み | シードが全滅 | 6 |
| `=== null` | `undefined` が画面に出た | 7 |

## 9. スキルの例

| 場面 | 役 | 例 |
|---|---|---|
| 配備系のコマンドの前（同期 ・ deploy ・ ビルド） | Generator ・ オーケストレーター | `convex-deploy-guard`（配備先を見分けて名乗る） |
| 提出 ・ 公開の前の点検 | オーケストレーター（`/release-check`） | `convex-reviewer`（**読むだけ**） |
| 読み取りの上限 ・ 費用の点検 | オーケストレーター | `convex-advisor` |

## 10. 土台への差し込み

### `docs/runbook.md` の「サーバー」表

| 項目 | 値 |
|---|---|
| E2E が見るサーバー | ローカル（例: `anonymous:anonymous-<アプリ名>`） |
| 実機 ・ 本番が見るサーバー | クラウド（例: クライアントの設定の `*_CONVEX_URL`）。**本番と同じに扱う** |
| クラウドへの同期コマンド | （実際のコマンド。**毎回ユーザーの承認**。常設の承認があるなら範囲を CLAUDE.md に） |
| 最後に同期したコミット | （同期のたびに `status.md` に記録） |
| ローカルの起こし方と確かめ方 | 4 のとおり ・ `http://127.0.0.1:3210/version` |
| 公開の入口の一覧 | `node docs/adapters/convex/list-public-functions.mjs convex` |

### `CLAUDE.md` に足す行

```markdown
- **`convex/` を触った回は、実機を試す前に、クラウドに届いているかを確かめる**（`git diff <最後に同期したコミット>..HEAD -- convex/` が空か）
- **同期 ・ `npx convex deploy` の前に配備先ガードを通す。実機が見ているデプロイメントは、区分が dev でも本番と同じに扱う**
- **同期の前表示の「クラウドにあって手元に無い関数」が 0 でなければ、最後に配ったビルドの木で呼んでいるかを先に見る**
```
