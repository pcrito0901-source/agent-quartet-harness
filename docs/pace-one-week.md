# 進め方: 1週間

> 最初の版を **1週間で出す** ための決まり（W1〜W7）。
> `docs/sprints/status.md` の「進め方」が `1週間` のときだけ効く。**無い ・ 未選択 ・ `通常` なら効かない。**
> **`通常` に書き換えれば、次の `/sprint` から元の流れに戻る**（下の「戻し方」）。

## なぜ

実運用（約76回のスプリント ・ 43日）で時間を食ったのは、次の3つだった。**どれも品質も下げていた**ので、
削るのは検査ではなく、この3つである。

| 時間を食ったもの | 実測 | この進め方での手 |
|---|---|---|
| **作り直し** | 76回のうち約28回が動いている画面の作り直し、約11回が実機の指摘の直し | 見本の承認（`/design`）と需要の確認（`/plan`）を先に済ませる。最初の版を8回に切る（W1） |
| **テストの重さ** | 約1,036件 ・ 1周 1.7〜5.9時間。1回のスプリントで2〜3周（走行ログ15本から） | 1回の自動の条件は10件まで（W2）。評価の前のフル回帰を省き、全件は合格の前の1回だけ（W4） |
| **時刻で落ちるテスト** | 「決まった時刻より前は撮れない」機能のテストが、朝に走らせると約30種類まとめて落ちた（延べ115件 ・ 約10時間の空回り）。走行14本すべてに赤があり、製品の不具合が直った赤は延べ6件だけだった | 時計を固定するテストを最初から作る（W3） |

1回のスプリントは平均で約13時間かかっていた（期間 1,007時間 ÷ 76回。夜や待ちを含む。コミットの日時から数えた）。
この速さのままでは1週間で約13回しか回らない。**回数を減らす（W1）と、1回を短くする（W2〜W5）の両方が要る。**

## 日割り

| 日 | やること | ユーザーの出番 |
|---|---|---|
| 0日目（半日） | 需要を確かめる → `/plan` → 確認事項にまとめて答える | 確認事項に答える |
| 1日目 | `/design` で全画面の見本 → まとめて承認 | **見本を見て直しを言い、承認する（この日がいちばん要る）** |
| 2〜5日目 | 1日2回ずつ、計8回の縦切り（1回 4〜6時間） | 朝と夕に、溜まった質問にまとめて答える ・ 実機で触る |
| 6日目 | 実機の確認 ・ `/release-check` ・ 課金と計測が届くか | 実機で触る ・ ストアの管理画面の作業 |
| 7日目 | 予備日 → 審査に出す（審査そのものは1週間の外） | 審査に出す（ユーザーの操作） |

**遅れたら、日を延ばす前に、翌週に回す機能を1つ増やす**（W7）。

## 決まり（1週間のときだけ）

| # | 決まり | 誰が |
|---|---|---|
| W1 | **最初の版は縦切り8回まで。** spec の「最初の版と翌週以降」に、8回に入る機能と、翌週以降に回す機能を分けて書く。8回に入らなければ、機能を翌週へ回す（回を詰め込まない） | Planner |
| W2 | **1回の契約の自動の条件は10件まで**（手動検証項目は別）。11件以上要るなら回を2つに割る（ただし W1 の8回に収める）。8回 × 10件で、全件はおよそ80件になる | Planner |
| W3 | **時刻 ・ 日付で動きが変わる機能は、Sprint 1 から時計を差し替えられる作りにする。** テストは時計を固定するか、データの時刻を「走らせた時刻」から相対で置く。「この時間帯の外で走らせない」（時刻の型）で逃がさない。差し替える作りが無ければ、改善提案ではなく Generator への差し戻し | Planner（契約に書く）・ Generator ・ Evaluator |
| W4 | **評価の前のフル回帰（`/sprint` の Phase C0）は省く。** 全件は Evaluator が合格の直前に1回だけ回す。全件が20分を超えたら、Evaluator が改善提案に書き、Planner が次の回でテストを絞る（約1,036件で1周2時間前後だった実測から、80件なら20分に収まる見込み） | オーケストレーター ・ Evaluator ・ Planner |
| W5 | **質問は1日2回（朝 ・ 夕）にまとめて出す。** 取り返しのつく既定を選んで進み、答えが来たら差し替える。取り返しのつかないもの（外向きの操作 ・ 配備 ・ 提出 ・ 支払い）だけは止まって待つ | オーケストレーター |
| W6 | **実機の確認は毎日1回。** その日に合格した木で配布のビルドを出し、`/release-check device <番号>` の表で触ってもらう（費用と枠は `docs/release-checklist.md` と付録の決まりどおり。枠を超えるなら1日おきに減らす） | オーケストレーター ・ ユーザー |
| W7 | **途中で増えた要望は、最初の版に入れるか翌週に回すかをユーザーに聞く。** 入れるなら、同じ大きさの機能を1つ翌週へ出す（8回を超えない）。翌週に回すものは `status.md` の送りに ID を付けて置く | オーケストレーター ・ Planner |

## 変えないもの

- 縦切り ・ 契約が実行できるテストになる ・ 1回の `/sprint` で1フェーズ ・ リトライ上限3 ・ 見本の承認 ・ **合格の前に全件が緑**
- Designer の段（見た目が変わらない回だけ省く。既存の決まりのまま）
- **品質の床は下げない。** 速くするのは「回数を減らす」「テストを軽く保つ」「待ちを減らす」ことで、検査を省くことではない

## 翌週から

最初の版を出した後は、**1週間ずつ同じ形で回す**（翌週に回した機能から、また8回まで）。
そのつど `/plan` で「最初の版と翌週以降」を書き直し、`/design` で新しい画面の見本だけを承認する。

## 戻し方

1. **このプロジェクトだけ戻す**: `docs/sprints/status.md` の「進め方」を `通常` に書き換える。
   次の `/sprint` から元の流れになる（評価の前のフル回帰あり ・ 回数と件数の上限なし ・ 時刻の型の扱いも元のまま）。
   もう書いた spec ・ 契約 ・ テストは消さなくてよい
2. **ハーネスごと戻す**: この決まりが入る前の版にタグ `v2.8.0` が付いている。
   その版に戻すか、この版を足したマージを `git revert` で打ち消す（履歴は残る）
