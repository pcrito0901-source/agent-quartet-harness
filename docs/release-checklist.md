# リリース確認チェックリスト

`/release-check`が参照する、人間とAIの共通チェックリスト。自動検証できない項目を合格扱いにしない。
技術ごとの項目とコマンドは、使う付録（`docs/adapters/*.md`）が足す。

**プロジェクトで提出の準備に使うときの書き方**: チェックボックスを表に起こし、各行に**担当**（ユーザー ／ オーケストレーター ／ Sprint N）と**状態**（未 ／ 済 ／ 要らない）を置く。
済にするときは、閉じたコミットのハッシュかユーザーの確かめの日を書く。**行は消さない**（要らなくなったら「要らない」と理由）。

## 0. 早い段階で名指す（`/release-check early` ・ 最初のテスター配布／公開ビルドの前）

提出の前夜に見つかると間に合わないもの。**スプリントの契約に入らず、外の管理画面で誰かが設定するもの**ほど見落とされる。

- [ ] アプリのアイコンと起動画面がテンプレートの見本のままでない（実運用で見本のまま29ビルド配布した）
- [ ] ソーシャルログインの OAuth クライアント ID がアプリとサーバーの両方に在り、同意画面が本番（実運用で提出の前夜に判明した）
- [ ] プライバシーポリシー・利用規約・サポートの公開 URL が実際に開ける
- [ ] 審査用のアカウント／データの用意の仕方が決まっている（アカウントの作成はユーザー）
- [ ] ストアの画面写真の寸法と、撮る画面の一覧がある
- [ ] 課金がある場合、商品 ID・価格・特典の文言の出どころが1つ

## 共通

- [ ] 全スプリントが合格
- [ ] 型チェック、lint、ユニットテスト、E2Eが成功（**E2E の全緑は自動の面の全緑。本番の面の保証ではない**）
- [ ] 未コミット変更の内容を説明できる
- [ ] 本番用の環境変数と秘密がリポジトリに含まれていない
- [ ] エラー監視、問い合わせ先、ロールバック方法が決まっている

## 本番の面（自動の面と違う場合 ・ 例: ネイティブのアプリ）

技術ごとの項目は、使う付録の「手動検証に回すもの」を足す。

- [ ] 自動の面だけでなく、配布用ビルドを作成した
- [ ] 実機またはテスター配布で主要導線を確認した（`/release-check device <n>` の一覧）
- [ ] 小さい画面と大きい画面でレイアウトを確認した
- [ ] オフライン、通信失敗、権限拒否を確認した
- [ ] カメラ、通知、写真、位置情報、マイク等の利用目的文を確認した
- [ ] 外部ログイン、ディープリンク、バックグラウンド動作を確認した
- [ ] 課金がある場合、購入・復元・解約後の状態を確認した

## 配布のビルドの決まり

ビルドと配布は外部の状態を変え、費用もかかる。**毎回同じ手順で、記録を残して出す。**
技術ごとのコマンドは使う付録の「配備 ・ ビルド ・ 配布」を見る（例: `adapters/expo-react-native` の 6）。

| # | 決まり | 理由 |
|---|---|---|
| B1 | **評価に合格した木から、まっさらな `git worktree` で出す**（作業中のフォルダから出さない） | 作業フォルダの未追跡ファイル（ローカル DB・キャッシュ）がアーカイブに混ざる。実運用ではビルドの道具が**入れ子の除外規則を当てられず**、ローカル DB（2GB 超）を丸ごと上げた。ルートの規則は効き、入れ子の規則だけが黙って効かない |
| B2 | **アーカイブの大きさを見る**。いつもの大きさから桁が違えば止めて中身を見る（ビルドの道具の、アップロードしない検査のコマンドで） | B1 の混入は名前でも警告でも気づきにくく、大きさでしか分からない |
| B3 | **ビルドの前の一括検査**を1本のコマンドにまとめ（例: `npm run build:gate`）、**1段でも落ちたら出さない** | 段の例: 設定の診断・本番の実行環境で動くかの確かめ・計測や課金のキーの有無・**サーバーに配備した記録と手元のサーバーのコードの突き合わせ** |
| B4 | **サーバー側のコードがクラウドに届いているかを、ビルドの前に確かめる**（`git diff <最後に配備したコミット>..<ビルドの木> -- <サーバーのディレクトリ>` が空） | E2E はローカルのサーバー、実機はクラウドのサーバーを見ていることがある。**同じコミットでもサーバーは別物でありうる**。実運用で E2E 全緑のまま、実機に新しいフィールドが `undefined` で届いた |
| B5 | **サーバーから公開の入口を消す配備は、端末に入っている古いビルドを壊す** | 配備の前に「クラウドにあって手元に無い入口」を数え、0 でなければ**最後に配布したビルドの木**で呼んでいるか grep する。呼んでいれば、配備の直後に新しいビルドを出す段取りを先に立てる |
| B6 | **送信の後に配布のタグを打つ**（例: `git tag -a release/<n> <木> -m "sent YYYY-MM-DD"`。名は付録が決める） | どのビルドがどの木かの台帳になる。古いビルドが呼ぶ入口を消してよいかの判定（B5）に使う |
| B7 | **費用と月の枠を `status.md` の「ビルドの台帳」に記録**し、枠が尽きそうなら止めてユーザーに言う | 無料枠・定額プランには月の上限がある。**追加の支払い・プランの変更はユーザーが決める** |
| B8 | **審査への提出（Submit for Review）と公開はユーザーの操作**。エージェントは出さない | 取り返しがつかない。エージェントは実機で1度も確かめていない |
| B9 | ビルドを配布したら `/release-check device <n>` で**そのビルドの実機チェックリストを作ってユーザーに渡す** | 手動検証項目はスプリントの契約に散らばっている。集めて渡さないと確かめられずに積み上がる |
| B10 | `--no-wait` を使わない。ビルドの完了は「待つ形のコマンド」を background で走らせて受け取る | 外部のクラウドは完了を知らせてくれない（`CLAUDE.md` の「起こす仕掛け」） |

## ストアの掲載（ストアに出す場合 ・ 例は付録）

- [ ] アプリの識別子（例: Bundle ID）、バージョン、ビルド番号が正しい
- [ ] アプリアイコン（見本のままでない）、起動画面、スクリーンショット（寸法）を用意した
- [ ] 名前、サブタイトル、説明文、キーワードを用意した
- [ ] サポートURLとプライバシーポリシーURLが有効
- [ ] プライバシーの申告（ストアの回答 ・ アプリに同梱する申告）、年齢区分を確認した
- [ ] 暗号化申告と輸出コンプライアンスを確認した
- [ ] 審査用メモと、必要な場合は審査アカウントを用意した
- [ ] テスター配布で最終ビルドを確認した

## 承認境界

ビルドのアップロード、テスター配布、審査提出、公開は外部状態を変更する。実行直前に対象アプリ、バージョン、配布先を示し、人間の明示承認を得る。

ユーザーが「テスター配布までのビルドと送信」に**常設の承認**を出すことはある。その場合も、範囲（どの木から・どこまで）と
毎回すること（B1〜B7）を `CLAUDE.md` に書き、**審査への提出・支払い・アカウントの操作は範囲に含めない**。
