このプロジェクトで Agent Quartet Harness が動く状態を整えてください。

## 1. 必須ファイルの配置確認

以下が存在するか確認し、欠けていれば作成する:

| パス | 役割 | 欠けている場合 |
|------|------|----------------|
| `.claude/hooks/guard.mjs` | 役割境界の強制 | プラグイン利用時は`${CLAUDE_PLUGIN_ROOT}`から直接使う。手動コピー方式ではプロジェクトへコピーする |
| `docs/design-tokens.*` | デザイントークンの正本 | 既定は `design-tokens.css` をコピー。**付録が別の形式を渡すならそちら**（2 で決まる。例: `adapters/expo-react-native/design-tokens.ts`） |
| `docs/rubric.md` | 採点アンカー | ハーネスのテンプレートをコピー |
| `docs/runbook.md` | 起動方法 | テンプレートを置く（Sprint 1 で Generator が実値を埋める） |
| `docs/sprints/status.md` | 進捗状態 | テンプレートを置く |
| `docs/design-references/` | 見本と目録（`/design` が作る）・ 方向づけの参考画像 | ハーネスの `docs/design-references/INDEX.md`（目録の雛形）をコピーする |
| `docs/adapters/` | 使う付録 | 2 で写す（付録が無ければ作らない） |

## 2. 技術の組み合わせを聞き、使う付録を配線する

土台はどの技術でも同じに動く。技術ごとの「どの面で評価するか ・ 何が手動になるか ・ どう配る ・ どこに罠があるか」は
**付録**（ハーネスの `adapters/<名前>/`）にある。ここで、このプロジェクトが使う付録を決めて配線する。
付録の置き場所は、プラグイン方式なら `${CLAUDE_PLUGIN_ROOT}/adapters/`、手動コピー方式なら写したハーネスの `adapters/`。

1. **見分ける**: 依存とファイル（`package.json` ・ アプリの設定 ・ サーバーのディレクトリ ・ ビルドの設定）を見て、
   各付録の「1. 見分け方」と照らす。まだ何も無い新しいプロジェクトなら、`/plan` で作る予定の技術を聞く
2. **聞く**: `AskUserQuestion` を1回だけ呼び、まとめて確かめる。見分けた結果を既定（おすすめ）にする
   - クライアント: Web ／ Expo・React Native ／ その他（名前を書いてもらう）／ 無し
   - サーバー: Convex ／ その他（名前）／ 無し
   - 配布: ストア ／ Web の公開 ／ 社内だけ ／ まだ決めていない
3. **写す**: 選んだ付録の `README.md` を `docs/adapters/<名前>.md` に写す。補助ファイルは付録の「土台への差し込み」の指示どおりに
   （例: `expo-react-native` → `docs/design-tokens.ts` と `scripts/release-build.mjs` ／ `convex` → `docs/adapters/convex/list-public-functions.mjs`）。
   写した付録の中の相対リンクは、ハーネスの `adapters/` を指す（正本はハーネス側）
4. **配線する**: プロジェクトの `CLAUDE.md` の末尾の「使う付録」表に、付録の名前 ・ パス ・ 主に読む役を書く。
   `CLAUDE.md` がまだハーネスの内容を持っていなければ、先にハーネスの `CLAUDE.md` を追記する（上書きしない）
5. **差し込む**: 付録の「土台への差し込み」節の行を、`docs/runbook.md` の表へ写す（値は例のまま。Sprint 1 の Generator が実値で埋める）。
   `CLAUDE.md` に足す行は「## ルール」の末尾へ。**常設の承認の行は写さない**（承認はユーザーが出すもの。例として案内だけする）
6. **付録の無い技術なら**: 「使う付録」表に「無し（土台だけ）」と書く。**土台だけで動く。**
   `docs/runbook.md` の「評価の面」に、回帰の E2E が何を操作するか（例: API ・ CLI ・ ブラウザ）を Sprint 1 で書くよう、
   Planner の C0-2 がそのまま求める。踏んだ罠は runbook の「既知のハマりどころ」に貯め、3つ以上たまったら
   `adapters/README.md` の見出しで付録に切り出すよう、ユーザーに案内する
7. 技術が変わったら、ここだけを再実行してよい（付録の追加 ・ 外し）

## 3. ガードのロジック検証

プラグイン方式ではプラグイン内のテストを実行する。

```bash
node --test "${CLAUDE_PLUGIN_ROOT}/.claude/hooks/*.test.mjs"
```

手動コピー方式ではプロジェクト内のテストを実行する。

```bash
node --test ".claude/hooks/*.test.mjs"
```

すべて緑になることを確認する。ロジックテストに加え、4エージェントのfrontmatter配線とPlaywright MCPのバージョン固定も検証される。

## 4. ガードの発火検証（これを省略してはならない）

**上の単体テストは「ガードのロジックが正しいこと」しか証明していない。**
フックが実際に発火するかは別問題である。ロジックが正しくても発火していなければ、
役割境界は存在しないのと同じ。「守っているつもり」が最も危険な状態である。

必ず**実際にサブエージェントを起動して**確認する:

1. Claude Codeのワークスペース信頼ダイアログを承認する。未信頼のフォルダではfrontmatterフックが読み飛ばされる。
2. **セッションを再起動する。** エージェント定義とフックはセッション開始時に読み込まれる。
   ファイルをコピーした同じセッションではエージェントは認識されない
   （`Agent type 'evaluator' not found` になる）
3. 再起動後、次を実行する:

   ```
   @agent-evaluator 動作確認です。src/dummy.ts に "hello" と書き込もうとしてみてください。ブロックされたらエラーメッセージをそのまま報告してください。
   ```

4. 期待する結果:

   ```
   [harness guard: evaluator] src/dummy.ts への書き込みは許可されていません。
   ```

5. **ファイルが作られてしまった場合、ガードは発火していない。** `claude --debug`のログで
   `skips its frontmatter hooks`またはパス解決エラーを確認する。プラグイン方式では
   `${CLAUDE_PLUGIN_ROOT}`、手動コピー方式では`${CLAUDE_PROJECT_DIR}`を使う。
   `.claude/agents/evaluator.md` の `command:` 行を一時的に差し替え、セッションを
   再起動してもう一度試す（パス依存を式から消すのが狙い）:

   ```
   command: node -e "require('fs').appendFileSync('hook-fired.log','FIRED cwd='+process.cwd()+String.fromCharCode(10))"
   ```

   | `hook-fired.log` | 判定と対処 |
   |---|---|
   | できた | フックは動いている。問題は起動コマンドのパス解決。ログの `cwd=` を見て `command:` を修正する |
   | できない | このビルドでは subagent frontmatter の `hooks:` が効いていない。役割境界はプロンプトレベルのみと割り切り、各フェーズ後に `git diff` で越境を目視確認する運用に切り替える |

6. 確認後、`src/dummy.ts` と `hook-fired.log` を削除し、`command:` を元に戻す

## 5. 前提の確認

- **Node.js が必要**（ガードスクリプトの実行に使う）。`node --version` で確認
- **Playwright MCP は設定不要**。Designer と Evaluator の frontmatter に inline 定義されており、
  エージェント起動時に検証済みの`@playwright/mcp@0.0.82`が自動的に立ち上がる（ブラウザを操作しないアプリでは使われないだけで、害は無い）

## 6. スキルの配線（役と場面）

ハーネスは**サードパーティのスキルを同梱しない**（ライセンスと更新の都合）。名前で参照するだけである。
ここでは、**役と場面**ごとに「どの種類のスキルが要るか」を決め、**実際に入っているスキルだけ**を配線する。
技術ごとの具体的なスキル名は、使う付録の「スキルの例」にある。

1. **入っているスキルを数える**: このセッションで使えるスキルの一覧を見る。ファイルで確かめるなら
   `.claude/skills/*/SKILL.md`（プロジェクト）・`~/.claude/skills/*/SKILL.md`（ユーザー）・
   `~/.claude/plugins/installed_plugins.json` とプラグインの `skills/`（プラグイン経由）の3か所。
   **0件が返ったら、探した場所のほうを疑う**（プラグイン経由のスキルは `~/.claude/skills/` に無い）
2. **下の表の場面ごとに、入っているものだけを選ぶ。** 入っていないものは書かず、入れ方を案内するだけにする
   （無いスキルを参照して壊れないように）

| 場面 | 役 | 要るスキルの種類 | 例（入っていれば ・ 付録の「スキルの例」も見る） | 決まり |
|---|---|---|---|---|
| 実装 | Generator | 技術のベストプラクティス | `react-native-best-practices` | |
| UI の仕上げ | Designer | デザイン | `ui-ux-pro-max` の本体 | **本番の面で崩れる部品を使わない**（例: ネイティブで Web 前提のスタイルの部品） |
| 評価 | Evaluator | 技術のベストプラクティス | 実装と同じもの | |
| 配備系のコマンドの前 | Generator ・ オーケストレーター | 配備先を見分けて名乗らせるガード | `convex-deploy-guard` | 実機が見ている先は、区分が開発用でも本番と同じに扱う |
| **提出 ・ 公開の前の点検** | オーケストレーター（`/release-check`） | **コードのレビュー**（セキュリティ ・ 入口の認証） | `convex-reviewer` ・ `security-review` | **読むだけ**。書き換えさせない |
| **ストアの文 ・ 利用者に見える文** | オーケストレーター → Planner か Designer | **文章を整える** | `natural-japanese` ・ `copywriting` ・ `metadata-optimization` | 文字数の上限を先に渡す。事実を足させない |
| **ビルドと配布** | オーケストレーター | **配布** | `eas-app-stores` ・ `asc-testflight-orchestration` | **審査への提出は使わない** ・ サブエージェントに打たせない |
| ストア ・ 管理画面の確かめ | オーケストレーター | 管理画面を読む | `asc-*` の読み取り系 | 状態を変える操作は毎回承認の後 |
| 数字の確かめ（計測 ・ 課金） | オーケストレーター | 計測 ・ 課金を読む | （計測 ・ 課金の MCP） | 読むだけ |

**決まり:**

- **役ごとに1〜2本まで。** スキルはサブエージェントのコンテキストを食う。**Planner には原則つけない**
- **オーケストレーターの場面のスキル**（点検 ・ 文 ・ 配布）は配線しない。その場面に来たときに Skill ツールで読み込む
- **手動コピー方式**: `.claude/agents/<役>.md` の frontmatter に `skills:` を書く（`hooks:` の行は消さない）
- **プラグイン方式**: プラグインのエージェント定義は書き換えない（更新で消える）。
  選んだスキルを `docs/runbook.md` の「スキル（役ごと）」表に書き、オーケストレーターがサブエージェントを起動するときに
  「使うスキル: ○○（Skill ツールで読み込んでから着手）」とプロンプトで渡す
- **`skills:` は絞り込みではない。** プラグインのスキルは、書かなくてもサブエージェントに届くことがある。
  「本番の面で崩れる部品を使わない」のような枷は、エージェントへのプロンプトか本文で掛ける
- **配線しただけで「使っている」と言わない。** 書き込みをしない確認だけのサブエージェントを起動し、
  そのスキルが届いているかを本人に答えさせて確かめる

## 7. スキルと MCP の提案

技術スタックと外部サービス（計測・課金・ストア・決済・DB/バックエンド・デザインツールなど）から、
効きそうなスキルと MCP を**3つまで**提案する（`CLAUDE.md` の「スキルと MCP の提案」の形）。
入れる・認証する・鍵を渡すのはユーザーの操作である。入れたスキルは 6 に戻って配線する。

## 8. ユーザーへの案内

準備が終わったら、次のステップを案内する:

```
/plan 作りたいものを1〜4行で
```

**ストアに出す・一般に公開するアプリなら、あわせて案内する:**
`/plan` の承認の直後に `/release-check early` を1回回し、アイコン・起動画面・ソーシャルログインの設定・公開 URL・
審査用アカウント・画面写真の寸法を**最初に名指す**。提出の前夜に見つかると間に合わないものばかりである。
