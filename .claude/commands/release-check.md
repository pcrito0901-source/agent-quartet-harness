リリースの準備状況を確認してください。これは**読み取りと検証だけ**を行うコマンドです。ビルドのアップロード、TestFlight配布、ストア提出、公開、APIキー作成は実行しません。

引数でモードを選ぶ:

| 引数 | モード | いつ使うか | 保存先 |
|---|---|---|---|
| `early` | **早期の穴の確認** | `/plan` の承認の直後、遅くとも**最初の TestFlight／公開ビルドの前** | `docs/releases/early-check.md` |
| `device <n>` | **ビルドごとの実機チェックリスト** | ビルド n を配布した直後 | `docs/releases/device-checks-build-<n>.md` |
| それ以外（`1.0.0` など） | **提出前の総点検** | ストア提出・公開の前 | `docs/releases/release-readiness.md` |

**道具**: ストアや課金のスキル・MCP（`asc-*` 系など）が入っていれば、**読み取りと確かめの用途だけ**で使う
（ビルドの一覧・メタデータ・審査の状態・画面写真の寸法の確かめ）。**提出（submit-for-review の族）・価格の変更・
テスターの追加など、状態を変える操作は使わない。** 入っていなくて手作業が重い所があれば、
レポートの末尾に `CLAUDE.md` の「スキルと MCP の提案」の形で3つまで提案する（入れるのはユーザー）。

## モード early —— 提出の前夜に見つかる穴を、最初に名指す

実運用では、次の穴が**提出の直前まで**見つからなかった:
アプリのアイコンがテンプレートの見本のまま29ビルド配布されていた ／ ソーシャルログインの OAuth クライアント ID が提出の前夜に判明した。
どれも「作る」ことより「誰かが外の画面で設定する」ことで、スプリントの契約に入らないため、誰も見ていなかった。

`package.json`・`app.json`／`app.config.*`・`eas.json`・`assets/` と `docs/spec.md` を読み、次を**有無と担当**で表にする（直さない）:

| # | 項目 | 見方 | 担当の既定 |
|---|---|---|---|
| E1 | **アプリのアイコンと起動画面がテンプレートの見本のままでないか** | `app.json` の `icon` ・ `splash` ・ `adaptiveIcon` が指すファイルを開いて見る。テンプレートの既定のファイル名・既定の絵・ハッシュが同じなら「見本のまま」 | ユーザー（絵を用意）→ Generator（差し替え） |
| E2 | **ソーシャルログイン**（Apple・Google など）の OAuth クライアント ID と、サーバー側の設定 | クライアント ID がアプリの設定（`app.json` の scheme・`eas.json` の env など）に在るか ／ サーバー側（認証の設定・許可するクライアント ID の一覧）に同じ ID が在るか ／ 同意画面が本番になっているか | ユーザー（外の管理画面）→ Generator |
| E3 | **公開 URL**: プライバシーポリシー ・ 利用規約 ・ サポート | 3つが実際に開けるか（下書きしか無い・ローカルにしか無いは「無い」） | ユーザー（公開）→ Planner（文面の案） |
| E4 | **審査用のアカウント／グループ／データ** | 審査員がサインインして主要な導線を最後まで見られるか。空のデータで渡すと審査員は何も見られない | ユーザー（アカウントの作成はエージェントがしない） |
| E5 | **ストアの画面写真の寸法** | 必要な端末サイズの寸法を控え、撮る画面の一覧があるか | ユーザー（実機で撮る） |
| E6 | Bundle ID ・ アプリ名 ・ 年齢区分 ・ 暗号化申告 ・ App Privacy の回答の材料 | 設定に値が在るか、回答の材料（何を集めて誰に渡すか）が文書に在るか | Planner（材料）→ ユーザー（入力） |
| E7 | 課金がある場合: 商品 ID・価格・特典の文言がアプリとストアと課金サービスで一致するか | 3か所の値の出どころが1つか | ユーザー（管理画面）→ Generator |

結果の各行に **状態（済／未／要らない＋理由）・担当・いつまでに**を書く。
「未」のうちユーザーにしかできないものは、`AskUserQuestion` で**まとめて**頼む（1件ずつ止まらない）。
スプリントで直すものは、Planner に契約か送りへ入れてもらう。

## モード device <n> —— ビルドごとの実機チェックリストを作る

E2E の全緑は **Web の全緑**であり、実機の保証ではない。実機でしか見えないものを、ビルドのたびに漏れなく手渡すための一覧を作る。

1. `docs/sprints/status.md` の「ビルドの台帳」から、**前のビルドの木**と**ビルド <n> の木**を読む
2. その間に合格したスプリントを `git log` と `status.md` で数え、各契約の **「手動検証項目」節**を全部集める
3. 次の見出しで `docs/releases/device-checks-build-<n>.md` に書く:
   - **このビルドで初めて確かめられるもの**（今回の回の手動検証項目）
   - **前のビルドで確かめられなかったもの**（前の一覧の未チェックを繰り越す）
   - **毎回見るもの**（サインイン・主要導線・課金がある場合は購入と復元）
   - 各行に「どの契約の何番から来たか」と「どう確かめるか（操作の手順を1〜3行）」
4. サーバー側のコードを触った回が含まれるなら、**そのコードがクラウドに届いているか**を先頭に書く
   （届いていなければ、実機で見える不具合は配備漏れの可能性が高い）
5. ユーザーに一覧のパスを渡し、「確かめた結果は `/feedback <n>` で」と案内する

## 通常モード —— 提出前の総点検

### 1. 現在地を確認

- `docs/spec.md`、`docs/sprints/status.md`、`docs/runbook.md`を読む
- 全スプリントが合格か確認する
- `git status --short`で未コミット変更を確認する
- `package.json`、`app.json`、`app.config.*`、`eas.json`からWebまたはExpo/React Nativeを判別する
- `docs/releases/early-check.md` があれば読み、「未」が残っていないか見る（無ければ early の表を先に作る）

### 2. 自動検証

存在するコマンドだけを実行し、推測したコマンドを追加しない。

- 型チェック
- lint
- ユニットテスト
- `npm run e2e`による全スプリント回帰（**合否には「Web で」と付ける**）
- production buildまたはExpo設定検証
- ビルドの前の一括検査があれば実行する（`docs/release-checklist.md` の「ビルドの前の一括検査」）

失敗した場合はそこで「準備未完了」とし、エラー、再現コマンド、差し戻し先を記録する。失敗を直すためのコード変更はこのコマンド内では行わない。

### 3. Expo / React Native追加確認

`docs/release-checklist.md`のネイティブ項目を確認する。Windowsから検証できない項目は合格扱いにせず、`未検証`として残す。

- 実機レイアウト
- カメラ、通知、位置情報、写真、マイク等の権限
- Appleログイン、ディープリンク、バックグラウンド動作
- アプリ内課金・サブスクリプション
- EASまたは別のmacOSビルド環境
- TestFlightでのインストールと主要導線
- 最新の `device-checks-build-<n>.md` の未チェックの行
- **サーバー側のコードがクラウドに届いているか**（最後に配備したコミットから、サーバーのディレクトリの差が 0 か）

### 4. App Store情報

秘密情報を表示・保存せず、次の有無だけを確認する。

- Bundle ID、バージョン、ビルド番号
- アプリアイコン（見本のままでないか）、起動画面、スクリーンショット（寸法）
- 説明文、キーワード、サポートURL、プライバシーポリシーURL（開けるか）
- Privacy ManifestとApp Privacy回答
- 年齢区分、暗号化申告、審査用メモ、審査アカウント

### 5. レポート

`docs/releases/release-readiness.md`へ次を保存する。

1. 判定: `準備未完了` / `ネイティブ確認待ち` / `提出承認待ち`
2. 実行したコマンドと終了結果
3. 未検証のネイティブ項目
4. App Store情報の不足
5. ブロッカーと担当
6. 人間が次に行う1つの操作

提出可能に見えても、自動送信はせず`提出承認待ち`で止める。**審査への提出（Submit for Review）はユーザーの操作であり、エージェントは出さない。**
