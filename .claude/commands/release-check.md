---
description: 公開・テスター配布・ストア提出の前に、変更を加えずリリース準備状況を確認する（early / device / security / 通常の4モード）
argument-hint: early | device <ビルド番号> | security | [バージョンまたはリリース名]
---

リリースの準備状況を確認してください。これは**読み取りと検証だけ**を行うコマンドです。ビルドのアップロード、テスター配布、ストア提出、公開、APIキー作成は実行しません。

引数でモードを選ぶ:

| 引数 | モード | いつ使うか | 保存先 |
|---|---|---|---|
| `early` | **早期の穴の確認** | `/plan` の承認の直後、遅くとも**最初のテスター配布／公開ビルドの前** | `docs/releases/early-check.md` |
| `device <n>` | **ビルドごとの実機チェックリスト** | ビルド n を配布した直後 | `docs/releases/device-checks-build-<n>.md` |
| `security` | **提出・公開の前の点検だけ**（通常モードの 3〜5） | 外部のテスターに配る前 ・ 公開の入口を足した回の後 | `docs/releases/security-check.md` |
| それ以外（`1.0.0` など） | **提出前の総点検** | ストア提出・公開の前 | `docs/releases/release-readiness.md` |

**道具**: ストアや課金のスキル・MCP（例: ストアの管理画面を読むスキル）が入っていれば、**読み取りと確かめの用途だけ**で使う
（ビルドの一覧・メタデータ・審査の状態・画面写真の寸法の確かめ）。**提出（submit-for-review の族）・価格の変更・
テスターの追加など、状態を変える操作は使わない。** 入っていなくて手作業が重い所があれば、
レポートの末尾に `CLAUDE.md` の「スキルと MCP の提案」の形で3つまで提案する（入れるのはユーザー）。
点検（通常モードの 3）では、入っていればコードのレビュー用のスキル（例: `convex-reviewer` ・ `security-review`）を**読むだけ**で使う。

道具や書き込みが安全装置（権限の確認 ・ ガード）に止められたら、回り道をせず、ユーザーが打つ1行か画面の手順を渡す（`CLAUDE.md` の「安全装置に止められたら」）。

## モード early —— 提出の前夜に見つかる穴を、最初に名指す

実運用では、次の穴が**提出の直前まで**見つからなかった:
アプリのアイコンがテンプレートの見本のまま29ビルド配布されていた ／ ソーシャルログインの OAuth クライアント ID が提出の前夜に判明した ／
課金を作ってから、**サーバーに購入の記録が1件も届かないまま**数週間が過ぎた（画面では買えているように見えていた）／
公開の直前に、**計測を間に合わせる回**が1回まるごと要り、その後も穴を埋める回がもう1回要った。
どれも「作る」ことより「誰かが外の画面で設定する」「届いたかを誰も見ていない」ことで、スプリントの契約に入らないため、誰も見ていなかった。

アプリとビルドの設定ファイル（使う付録の「見分け方」が名指すもの。例: `package.json` ・ アプリの設定 ・ ビルドの設定）・ アセットのフォルダ ・ `docs/spec.md` を読み、次を**有無と担当**で表にする（直さない）:

| # | 項目 | 見方 | 担当の既定 |
|---|---|---|---|
| E1 | **アプリのアイコンと起動画面がテンプレートの見本のままでないか** | アプリの設定がアイコン・起動画面として指すファイルを開いて見る。テンプレートの既定のファイル名・既定の絵・ハッシュが同じなら「見本のまま」 | ユーザー（絵を用意）→ Generator（差し替え） |
| E2 | **ソーシャルログイン**（Apple・Google など）の OAuth クライアント ID と、サーバー側の設定 | クライアント ID がアプリの設定（URL スキーム ・ ビルドの環境変数など）に在るか ／ サーバー側（認証の設定・許可するクライアント ID の一覧）に同じ ID が在るか ／ 同意画面が本番になっているか | ユーザー（外の管理画面）→ Generator |
| E3 | **公開 URL**: プライバシーポリシー ・ 利用規約 ・ サポート | 3つが実際に開けるか（下書きしか無い・ローカルにしか無いは「無い」） | ユーザー（公開）→ Planner（文面の案） |
| E4 | **審査用のアカウント／データ** | 審査員がサインインして主要な導線を最後まで見られるか。空のデータで渡すと審査員は何も見られない | ユーザー（アカウントの作成はエージェントがしない） |
| E5 | **ストアの画面写真の寸法** | 必要な端末サイズの寸法を控え、撮る画面の一覧があるか | ユーザー（実機で撮る） |
| E6 | アプリの識別子 ・ アプリ名 ・ 年齢区分 ・ 暗号化の申告 ・ プライバシーの回答の材料 | 設定に値が在るか、回答の材料（何を集めて誰に渡すか）が文書に在るか | Planner（材料）→ ユーザー（入力） |
| E7 | 課金がある場合: 商品 ID・価格・特典の文言がアプリとストアと課金サービスで一致するか | 3か所の値の出どころが1つか | ユーザー（管理画面）→ Generator |
| E8 | **利用者の投稿 ・ コメント ・ やりとりがある場合**: 審査で見られる機能（通報 ・ ブロック ・ 自分の投稿やコメントの削除 ・ アプリの中からのアカウント削除）が計画に入っているか | `docs/spec.md` と契約に、サーバーと画面の入口の**両方**が条文としてあるか | Planner（契約）→ Generator |
| E9 | **外部サービスの管理画面の作業の分担表**（`docs/release-checklist.md`）を作ったか | 作業ごとに「道具で書けるか ・ 担当 ・ 文字数の上限 ・ 記録の有無」が埋まっているか | オーケストレーター（表）→ ユーザー（画面の作業） |
| E10 | **課金がある場合: 購入がサーバーに記録され、機能が開くまで**を、最初のテスター配布の前に1回通す段取りがあるか | 誰が ・ いつ ・ どのテスト用の購入で通すかが決まっているか。**画面で「買えた」だけで済ませず、サーバー側の購入の記録（権限）が立ち、有料の機能が開くことまでを見る**予定か | Generator（受け口）→ ユーザー（課金サービスの通知の宛先 ・ テスト用の購入） |
| E11 | **計測がある場合: 主な操作のイベントが、分析の画面に届くこと**を公開の前に確かめる段取りがあるか | 送るイベントの一覧（登録 ・ 中心の操作 ・ 課金など）があり、**配布用のビルドで1回ずつ起こして、分析の画面に届いたかを読む**予定か（コードに送る処理が書いてあることだけで済ませない） | Generator（送る側）→ オーケストレーター（届いたかを読む） |

結果の各行に **状態（済／未／要らない＋理由）・担当・いつまでに**を書く。
「未」のうちユーザーにしかできないものは、`AskUserQuestion` で**まとめて**頼む（1件ずつ止まらない）。
スプリントで直すものは、Planner に契約か送りへ入れてもらう。

## モード device <n> —— ビルドごとの実機チェックリストを作る

E2E の全緑は **Web の全緑**であり、実機の保証ではない。実機でしか見えないものを、ビルドのたびに漏れなく手渡すための一覧を作る。

1. `docs/sprints/status.md` の「ビルドの台帳」から、**前のビルドの木**と**ビルド <n> の木**を読む
2. その間に合格したスプリントを `git log` と `status.md` で数え、各契約の **「手動検証項目」節**を全部集める
3. 次の見出しで `docs/releases/device-checks-build-<n>.md` に書く:
   - **このビルドで初めて確かめられるもの**（今回の回の手動検証項目）
   - **前のビルドで確かめられなかったもの**（前の一覧の未チェックを繰り越す）
   - **毎回見るもの**（サインイン ・ 主要導線 ・ 課金がある場合は購入と復元 —— **画面で買えたことに加え、サーバーに購入の記録が立ち、有料の機能が開くこと** ・
     計測がある場合は、そのビルドで起こした主な操作のイベントが分析の画面に届いていること）
   - 各行に「どの契約の何番から来たか」と「どう確かめるか（操作の手順を1〜3行）」
4. サーバー側のコードを触った回が含まれるなら、**そのコードがクラウドに届いているか**を先頭に書く
   （届いていなければ、実機で見える不具合は配備漏れの可能性が高い）
5. ユーザーに一覧のパスを渡し、「確かめた結果は `/feedback <n>` で」と案内する

## モード security —— 点検だけを回す

通常モードの **3（提出・公開の前の点検）・ 4（機能と画面の入口の対応表）・ 5（増え続けるデータ）** だけを行い、
`docs/releases/security-check.md` に書く。外部のテスターに配る前と、公開の入口を足した回の後に回す。

## 通常モード —— 提出前の総点検

### 1. 現在地を確認

- `docs/spec.md`、`docs/sprints/status.md`、`docs/runbook.md`を読む
- 全スプリントが合格か確認する
- `git status --short`で未コミット変更を確認する
- 使う付録（`docs/adapters/*.md`）を読み、自動の評価の面と本番の面を確かめる
- `docs/releases/early-check.md` があれば読み、「未」が残っていないか見る（無ければ early の表を先に作る）

### 2. 自動検証

存在するコマンドだけを実行し、推測したコマンドを追加しない。

- 型チェック
- lint
- ユニットテスト
- 回帰の E2E の全件（**合否には「どの面で」を付ける**。例: 「Web で」）
- 本番用のビルド、または設定の検証（付録や runbook のコマンド）
- ビルドの前の一括検査があれば実行する（`docs/release-checklist.md` の「ビルドの前の一括検査」）

失敗した場合はそこで「準備未完了」とし、エラー、再現コマンド、差し戻し先を記録する。失敗を直すためのコード変更はこのコマンド内では行わない。

### 3. 提出・公開の前の点検（標準の段 ・ 読むだけ）

**なぜ**: 開発中に「テストのため」に開けた口は、開発用の設定を閉じても別の場所で開いていることがある。
実運用で、提出の直前に、**ログインなしで全利用者の個人的な記録が読める口が4つ**見つかった。

1. **サーバーの公開の入口をすべて列挙し、数を書く**（使う付録の「サーバーの公開の入口」の方法。台本があればそれ。例: `adapters/convex` の `list-public-functions.mjs`）
2. 各入口を次のどれかに仕分ける。**どれにも当たらない入口はブロッカー**

   | 仕分け | 確かめること |
   |---|---|
   | 認証が要る | 入口の頭で認証し、**持ち主やメンバーを照合している**（ログインしていても、他人のデータは返らない） |
   | 開発用の関門の後ろ | 関門が本番で閉じている。本番の向き先で1度呼んで拒まれることを確かめる（**本番に書き込む呼び方はしない**。呼べないなら手順をユーザーに渡す） |
   | 公開でよい | 誰が呼んでも困らない理由を1行で書く（例: アプリの版の文言を返すだけ） |

3. **定期処理は、外から呼べない内部の入口から呼んでいるか。** 定期処理のために公開にした入口はブロッカー
4. **テスト用の入口が本番で開いたままになっていないか。** テスト用 ・ シード ・ 開発用のログインの入口をすべて名指し、
   **同じ1つの関門**を通るかを見る。開発用の設定を1つ閉じても、別の判定（別の環境変数 ・ 関門を通らない口）で開いていることがある
5. **秘密がクライアントの束やリポジトリに入っていないか**（クライアントに渡る環境変数 ・ 設定ファイル ・ 履歴）
6. 入っていればコードのレビュー用のスキルに読ませる。**書き換えさせず、指摘だけ出させる**。指摘は自分で入口を開いて確かめてから表に入れる
7. 結果を「入口 ・ 仕分け ・ 根拠（ファイルと行）・ ブロッカーか」の表で `docs/releases/security-check.md` に書く。
   **直すのはこのコマンドではない**（ブロッカーは Planner の契約を通して Generator へ）

### 4. 機能と画面の入口の対応表

**なぜ**: サーバーに機能があっても、画面に入口が無ければ、利用者も審査員も使えない。
実運用で、コメントの削除はサーバーにあったのに、画面に入口が無かった。

ストアの審査で見られる機能について、サーバーと画面を対応させる（利用者の投稿 ・ やりとりがあるアプリでは必須）:

| 機能 | サーバーの入口 | 画面の入口（どの画面のどの操作） | 測っているテスト | 状態 |
|---|---|---|---|---|
| 通報 | | | | |
| ブロック | | | | |
| 自分の投稿の削除 | | | | |
| 自分のコメントの削除 | | | | |
| アカウントの削除（アプリの中から） | | | | |
| 課金があるなら: 購入の復元 ・ 解約の案内 | | | | |

- **「サーバーにあって画面に無い」「画面にあってサーバーに無い」はブロッカー**
- 画面の入口は、ソースを検索するだけでなく、自動の面で押して届くかで確かめる（既存の E2E があればその名を書く）
- 審査の役に立つ機能（審査用のアカウントで見られるか）も同じ表で見る

### 5. 増え続けるデータの読み方

**なぜ**: 日々増える表（記録 ・ 予約 ・ 通知 ・ ログ）を毎回全件読むと、いずれ1回の読み取りの上限を越え、定期処理ごと止まる。
実運用で、予約の記録の全件読みが上限を越え、テストのデータ作りが全滅した。

- 日々増える表を名指し、それを読む箇所で**絞り込みの無い全件読み**をしていないかを見る（技術ごとの書き方と上限は付録。例: `adapters/convex` の 6）
- 見つけたら「索引で範囲を絞る ・ 件数の上限 ・ ページ送り」のどれで直すかを添えて、ブロッカーか送りかを決める

### 6. 本番の面の追加確認（自動の面と本番の面が違う場合）

`docs/release-checklist.md` の「本番の面」の項目と、付録の「手動検証に回すもの」を確認する。自動で検証できない項目は合格扱いにせず、`未検証`として残す。

- 実機のレイアウト（小さい画面と大きい画面）
- カメラ、通知、位置情報、写真、マイク等の権限
- 外部ログイン、ディープリンク、バックグラウンド動作
- アプリ内課金・サブスクリプション（**テスト用の購入でサーバーに購入の記録が立ち、有料の機能が開くか**。サーバーの記録が0件なら、画面で買えても「未検証」）
- 計測（**主な操作のイベントが分析の画面に届いているか**。送る処理がコードにあるだけなら「未検証」）
- 配布用ビルドの環境（付録のビルド方式）
- テスター配布でのインストールと主要導線
- 最新の `device-checks-build-<n>.md` の未チェックの行
- **サーバー側のコードが本番のサーバーに届いているか**（最後に配備したコミットから、サーバーのディレクトリの差が 0 か）

### 7. ストア・公開先の情報

秘密情報を表示・保存せず、次の有無だけを確認する。

- アプリの識別子（例: Bundle ID）、バージョン、ビルド番号
- アプリアイコン（見本のままでないか）、起動画面、スクリーンショット（寸法）
- 説明文、キーワード、サポートURL、プライバシーポリシーURL（開けるか）
- プライバシーの申告（ストアの回答 ・ アプリに同梱する申告）
- 年齢区分、暗号化申告、審査用メモ、審査アカウント
- **外部サービスの管理画面の作業の分担表**（`docs/release-checklist.md`）が埋まっていて、ユーザーの担当の行に手順と貼り付け用の文が渡っているか
- **外部のテスターに配る前に、開発用のログイン（審査用 ・ テスト用の裏口）を閉じたか**（3 の 4 と同じ関門で見る）

### 8. レポート

`docs/releases/release-readiness.md`へ次を保存する。

1. 判定: `準備未完了` / `本番の面の確認待ち` / `提出承認待ち`
2. 実行したコマンドと終了結果
3. 点検（3〜5）の要約: 公開の入口の数 ・ 仕分けの内訳 ・ 対応表の穴 ・ 全件読みの箇所（詳細は `security-check.md`）
4. 未検証の本番の面の項目
5. ストア・公開先の情報の不足
6. ブロッカーと担当
7. 人間が次に行う1つの操作

提出可能に見えても、自動送信はせず`提出承認待ち`で止める。**審査への提出（Submit for Review）はユーザーの操作であり、エージェントは出さない。**
