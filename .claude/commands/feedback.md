ビルド $1 で見つかった実機の指摘を受けます。あなたはオーケストレーターです。

E2E の全緑は **Web（または自動化できた面）の全緑**であり、実機の保証ではない。
実機の指摘は、パイプラインの外から入ってくる**いちばん確かな証拠**である。
このコマンドは、それを取りこぼさず・言い換えて意味を落とさず・次のスプリントの契約に変えるための型である。

## このコマンドの最重要ルール

- **原文を先に残す。** 要約・分類・解釈はその後。言い換えた時点で意図が落ちる
- **質問は1度にまとめて聞く。** 1件ごとに止まらない
- **Planner は質問できない**（サブエージェントは `AskUserQuestion` を使えない）。聞くのはオーケストレーターの仕事
- **オーケストレーターは直さない。** 「小さい指摘だから自分で」は禁止。契約を通す

## 手順

### 1. 原文を記録する

指摘を `docs/sprints/status.md` の末尾に節を立てて**原文のまま**写す（引数に無ければ `AskUserQuestion` で聞く）。

```markdown
## 実機の指摘（ビルド $1 ・ YYYY-MM-DD HH:MM 受け取り）

| # | 原文（ユーザーの言葉のまま） | 画面 | 添付 |
|---|---|---|---|
| 1 | 「〜が押せない」 | グループの一覧 | スクリーンショット1枚 |
| 2 | ... | ... | ... |
```

- スクリーンショットがあれば `docs/sprints/feedback-build-$1/` に置き、表からパスで指す
- 1文に2つの原因が混ざっていることがある（例: 前半はサーバーが古いだけ、後半は本物の欠陥）。
  **割ってから番号を振る**

### 2. 先に「サーバーが古いだけ」を疑う

実機とテストが別のサーバー（クラウドとローカルなど）を見ている構成では、
**同じコミットでもサーバー側のコードは別物でありうる。** 指摘を「デザインの問題」「実装の欠陥」に分類する前に:

- 最後にクラウドへ配備したコミットから、サーバーのコード（例: `convex/` `server/` `api/`）に差があるか
  （`git diff <最後に配備したコミット>..<ビルドの木> -- <サーバーのディレクトリ>`）
- その画面が読むフィールドは、いつ足されたか

差があれば、その指摘は**配備すれば消える**可能性が高い。契約を立てる前に、配備の要否をユーザーに仰ぐ。

> 実運用での実害: 実機の「表示がよく分からない」をデザインの問題と読みかけたが、原因はサーバーの配備漏れで、
> 実機には新しいフィールドが `undefined` で届いていた（E2E はローカルのサーバーを見ていたので全緑だった）。

### 3. 答えが要る点を、1度にまとめて聞く

各指摘について「どう直すか」が1通りに決まらないもの（案が複数ある・好みが分かれる・仕様の変更になる）を洗い出し、
**`AskUserQuestion` を1回だけ呼んで全部まとめて聞く**。

- 各問いに**既定（おすすめ）**を付ける。「決めていただけなければ既定で進めます」と書く
- 見た目を「詰める／削る／寄せる」指摘は、言葉で聞かずに**案を2〜3枚撮って見せる**（`CLAUDE.md` のルール ・ Designer が撮る）
- 指摘の確かめや直しに外部サービスの道具（計測・課金・ストアの MCP など）が効くなら、**同じ問いの束で3つまで提案する**
  （`CLAUDE.md` の「スキルと MCP の提案」。入れるのはユーザー・変更できる権限は既定で切る）
- 答えは `status.md` の同じ節に**原文のまま**足す

### 4. Planner に「実機の指摘（ビルド $1）」の回の契約を書かせる

`@agent-planner` を起動し、次を渡す:

- 出どころ: `docs/sprints/status.md` の「実機の指摘（ビルド $1）」節（**Planner は原文を直に聞いていない**と契約に明記させる）
- 契約の題: `Sprint N: 実機の指摘（ビルド $1）—— <要約>`
- 各条文が**どの指摘の番号から来たか**を契約に書くこと
- 決定（仕様の変更）が生まれたら `docs/product-direction.md` に追記すること（決定の台帳 ・ `planner.md`）
- 既存のテストを覆す変更なら、契約の R 表（付け替えの見込み）に先に並べること
- 実機でしか確かめられないものは「手動検証項目」節へ

### 5. 提出の前／後で振り分ける

ストアの審査や公開の日が決まっている場合、各指摘を振り分ける:

| 振り分け | 行き先 |
|---|---|
| **提出の前に要る**（落ちる・審査で弾かれる・データを失う・誤解を招く） | この回の契約へ |
| **提出の後でよい**（好み・改善・新機能） | **送り**（ID を振って文書に残す。口約束にしない） |

送りは `status.md` の「送り」表に ID 付きで置く。**まだ存在しない ID を文書に書かない**
（範囲や予告を ID の形で書くと、走査が実在と数えて番号が狂う）。

### 6. 締める

1. `git add docs/sprints/status.md`（スクリーンショットを置いたなら `docs/sprints/feedback-build-$1/` も）して
   `git commit -m "feedback: ビルド $1 の実機の指摘を記録"`
2. ユーザーに報告する（`CLAUDE.md` の「ユーザーへの報告」の形）:
   - いまどこ（何件受け取り、何件を契約へ、何件を送りへ）
   - あとどのくらい（次の回の見込み）
   - あなたに頼むこと（答えていない問いがあれば）
3. 次のステップとして `/sprint N` を案内する

## スプリントの途中で追加の指摘が来たら

回を立て直さない。**契約への純粋な追記**として受ける。

1. 原文を `status.md` の同じ節に**追加の指摘**として足す（時刻つき）
2. `@agent-planner` に、契約の末尾へ **§N（追記）** を足させる
   - **既存の節は1字も書き換えない。** 足すだけ（差し戻しの判定が「どの版の契約で測ったか」を言えなくなるため）
   - 追記の節には、条文・R 表の追加行・手動検証項目・触らない範囲を、その節の中だけで書く
   - 追記が純粋な追記であることを確かめる（追記前のファイルの長さで先頭を切り出して、追記前と完全一致）
3. 決定が変わるなら `docs/product-direction.md` にも追記する（**契約とは別のコミットで**）
4. いま走っている段（Generator など）には、追記のパスを渡して続きから進めさせる
