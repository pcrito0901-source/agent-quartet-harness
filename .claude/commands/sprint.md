description: 指定スプリントの「次の1フェーズだけ」を実行して停止する
argument-hint: <スプリント番号>

Sprint $1 の **次の1フェーズだけ**を実行してください。あなたはオーケストレーターです。

## このコマンドの最重要ルール

**1回の呼び出しで1フェーズだけ実行し、必ず停止する。**
パイプライン全体を続けて回してはならない。

理由: 全フェーズを1ターンで回すと、セッションが長時間占有されてユーザーが割り込めず、
サブエージェントは最終テキストしか返さないため途中経過も見えない。
**1フェーズごとに制御をユーザーへ返すことが、このコマンドの目的である。**

「効率のために続けて実行しよう」と考えてはならない。それは目的に反する。

## 手順

### 1. 現在地を判定する

`docs/sprints/status.md` を読み、Sprint $1 のフェーズを確認する。

| 現在のフェーズ | 次に実行するもの |
|---|---|
| 計画済み で、契約に「見た目の案」節がある | **Phase A0: 見た目の案** |
| 未着手 / 計画済み / 案選択済み | **Phase A: 実装** |
| 実装済み | **Phase B: デザイン**（見た目が変わらない回は省いて `デザイン省略` にし、次の Phase C0 へ） |
| デザイン済み / デザイン省略 | **Phase C0: 評価の前のフル回帰**（スイートが小さいうちは省いて Phase C へ） |
| 回帰済み | **Phase C: 評価** |
| 不合格 | 評価レポートの「差し戻し先」に応じて **Phase A または B** |
| 合格 | 何もしない。次スプリントを案内して終了 |

事前確認:
- Sprint $1 より前が全て `合格` か（でなければ中断して報告）
- `docs/sprints/sprint-$1/contract.md` が存在するか（無ければ `/plan` を案内）
- **画面のあるアプリなら、`status.md` に `見本: 承認済み` か `見本: 不要` があるか**（無ければ `/design` を案内して止まる）。
  見本の段より前の版で始めたプロジェクトは、ユーザーに確かめたうえで `見本: 不要（途中から導入。新しく作る／変える画面から /design）` と書いて進めてよい
- **契約の「この回で作る／変える画面」が、`docs/design-references/INDEX.md` に承認済みで載っているか**
  （載っていない画面があれば、`/design <画面ID>` を案内して止まる。見本の無い画面を実装しながら決めない）
- リトライ回数が **3 以上**なら実行せず、`AskUserQuestion` でユーザーに判断を仰ぐ
  （契約を見直す / 該当条件を外す / もう3ラウンド試す）

### 2. 該当フェーズを1つだけ実行する

サブエージェントを起動するときは、`docs/runbook.md` の「スキル（役ごと）」表にその役のスキルがあれば、
「使うスキル: ○○（Skill ツールで読み込んでから着手）」とプロンプトに添える（プラグイン方式ではこれが配線になる）。
契約に「道具の提案」節があれば、起動の前にまとめて `AskUserQuestion` でユーザーに聞き、答えを `status.md` に書く。

**Phase A0: 見た目の案** —— 見た目を「詰める／削る／1画面に収める」回だけ。`@agent-designer` を**案モード**で起動する。渡すもの:
- 契約の「見た目の案」節と、元になったユーザーの言葉（原文のまま）
- 書き出し先: `docs/sprints/sprint-$1/design-options.md` と `docs/sprints/sprint-$1/options/`
- 「本実装はしない。量の違う案を2〜3枚撮って、作業ツリーを着手前に戻して終える」こと

終わったら案の画像をユーザーに見せ、`AskUserQuestion` で選んでもらう。答えを `design-options.md` と
`status.md` に書き、フェーズを `案選択済み` にする。**選ぶ前に Phase A に進まない。**
（契約に「見た目の案」節が無くても、ユーザーの指摘がこの種の直しなら、Planner に節の追記を頼んでからここを通す）

**Phase A: 実装** — `@agent-generator` を起動する。渡すもの:
- 契約: `docs/sprints/sprint-$1/contract.md`
- 契約が名指す画面の**承認済みの見本**のパス（`docs/design-references/INDEX.md` から引く）。
  **画面の骨格（どの面があり、どの順に並ぶか）は、最初から見本に合わせて作る**こと。見本に無い面を足さない
  （骨格を後から Designer が組み替えると、テストの付け替えが起きる）
- 報告の書き出し先: `docs/sprints/sprint-$1/generator-report.md`
- 差し戻しの場合は前ラウンドの評価レポートのパス

**Phase B: デザイン** — `@agent-designer` を起動する。渡すもの:
- `docs/sprints/sprint-$1/generator-report.md` を読むこと
- 契約が名指す画面の**承認済みの見本**に合わせること（骨格 ・ 文言 ・ 配置。見本と違うところは完了報告の「見本との差」に書く）
- `design-options.md` があれば、**選ばれた案をそのままの量で入れる**こと
- 報告の書き出し先: `docs/sprints/sprint-$1/designer-report.md`

**Designer を省く判断**（Phase B の代わり）—— 契約を読み、画面の見た目が変わらない回
（サーバーだけ・文言の中身だけ・テストや文書だけ）なら Designer を起動せず、`status.md` にフェーズ `デザイン省略` と**省いた理由**を書く。
迷ったら省かない。

**Phase C0: 評価の前のフル回帰**（オーケストレーターが自分で回す。サブエージェントは起動しない）
1. `git status` が clean で、走っているサブエージェントがいないこと（またはコミットを控えさせたこと）を確かめる
2. 測る木（`git rev-parse HEAD`）と開始の時刻を控え、全件を1回だけ走らせる。**走行中は誰もコミットしない**（記録は scratchpad に書き溜める）。
   **時刻の型（R 表 ・ spec の頭の注記）があるスイートは、その時間帯の外で始めない**
3. 赤を一覧にし、契約の R 表と突き合わせる。**時刻の型の赤は、その本だけを時間帯の中で（または時計を差し替えて）取り直す**（全件を回し直さない）。
   **R 表に無い赤**があれば `@agent-planner` に R 表への行の追記（付け替え先）を頼む
4. `status.md` に、測った木・開始と終了の時刻・本数・赤の一覧（時刻の型と取り直しの結果を分けて）・所要時間を書き、フェーズを `回帰済み` にする
5. 走行を待つ見張りは1つだけ。時間切れで足し直さない（`CLAUDE.md` の「起こす仕掛け」）

**Phase C: 評価** — `@agent-evaluator` を起動する。渡すもの:
- 契約と両報告のパス
- 評価レポートの書き出し先: `docs/sprints/sprint-$1/evaluation-{ラウンド番号}.md`
- Phase C0 の結果（測った木と赤の一覧）。付け替えの途中は触ったファイルとこの回の spec だけを走らせ、
  **合格を出す直前に Sprint 1..$1 の全件を1回**走らせること

**仕上げ（段E ・ 凍結の基準を使うプロジェクトだけ）** —— 過去の回の spec（と、守りたい製品のファイル）を
「基準のコミット」と突き合わせて見張る仕組み（**凍結**）を入れているなら、合格の前に次を通す。
凍結は、赤を消して緑にすることをテストの側から防ぐ。基準のコミットは1つのファイル（例: `e2e/freeze-baseline.ts`）に置き、オーケストレーターだけが進める。

1. **E-1**（Evaluator）評価文書に回の終わり（round-end）を書く
2. **E-2**（オーケストレーター）まだ進めていない基準のまま、基準を読む spec だけを単独で回す
3. **E-3**（Evaluator）基準から HEAD までの spec の差を仕分ける（題名の数 ・ `expect(` の数が減っていない ・ skip が増えていない ・ 消えたファイルが無い）。E2E は回さない
4. **E-4**（オーケストレーター）基準を HEAD へ進める（基準のファイルだけを変える1コミット）
5. **E-5**（オーケストレーター）フル回帰を単独で回す
6. **E-6**（Evaluator）E-5 の結果を読んで最終の合否を書く（テストは回さない）

- **基準を進めた後（E-4 の後）に製品や spec が動いたら（契約の追記の直しなど）、基準を進め直してから E-5 を回す。**
  動いた差が基準の外に残ると、凍結の見張りが次の回でそれを「破れ」と読む
- 赤が出て直しが入ったら、E-1 からやり直す

### 3. 後始末して停止する

1. **報告ファイルが実在するか確認する。** 無ければ書き出しを再依頼する
   （サブエージェントは独立コンテキストのため、チャット出力は次のエージェントから見えない）
2. `docs/sprints/status.md` を更新する（フェーズ、判定、リトライ回数、最終更新日）
3. 変えたパスを名指して `git add <パス…>` し、`git commit -m "sprint-$1: <フェーズ名>"`
   （`git add -A` は、並走中の他の役の書きかけやローカルの秘密・データのファイルを巻き込む）
4. ユーザーに報告する:
   - 実行したフェーズと結果の要約
   - **次に実行するコマンド**（例: 「デザインに進むなら `/sprint $1` を再実行してください」）
   - 評価が合格だった場合は、`/polish $1` でデザインを手直しできること、
     または次スプリントに進めることを案内する
5. **停止する。** 次のフェーズを勝手に始めない

## 絶対のルール

- **1呼び出し = 1フェーズ。** 続けて回さない
- **オーケストレーターは実装しない。** 「小さい修正だから自分で」は禁止。
  パイプラインの検証性が失われる
- **リトライ上限は3。** 同じ失敗を3回繰り返すのは、多くの場合エージェントではなく契約の問題
- Generator に差し戻した場合、修正後は Designer も再実行する
  （実装変更でデザインが崩れている可能性があるため）
- 各フェーズでコミットする。差し戻しで壊れたら `git revert` で戻せることが安全弁になる
- **E2E の走行は同時に1本だけ。** フル回帰の走行中は誰もコミットしない
- 1フェーズの中では止まらない。待つなら、何を待っていて何が自分を起こすかを言えること（`CLAUDE.md` の「長く回すための決まり」）
